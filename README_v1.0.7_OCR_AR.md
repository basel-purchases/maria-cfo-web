# Maria CFO Web v1.0.7 — تصحيح أرقام OCR لفواتير الشراء

تاريخ الإصدار: 23 تشرين الأول 2026. **الأساس:** حزمة Maria CFO Web v1.0.6 الكاملة؛ هذه الحزمة تحتوي المشروع الكامل مجددًا **دون `config.js`**.

## سبب الخلل (مثبت بإعادة إنتاجه)

أرسل المستخدم نص OCR على شكل جدول Markdown من فاتورة خضار، يحتوي على 15 بندًا وأعمدة: «السلسل / القيمة الإجمالية ليرة سورية / نوع البضاعة / العدد / كيلو صافي / السعر» بأرقام عربية وفارسية مثل `١٦٤١٥` و`٠,٨` و`٨,٤`.

في v1.0.6 كان المحلل يفقد حدود الأعمدة، ثم يشترط تطابق حاصل ضرب الكمية بالسعر مع الإجمالي لإظهار أرقام البند. إذا اختلفت القراءة الحسابية كانت الكمية والسعر تُتركان فارغتين **على الرغم من وجودهما في نتيجة OCR**. وتفسير الفاصلة العشرية العربية `٠,٨` لم يكن صحيحًا.

عند تشغيل **النص نفسه** على الإصدار السابق: 15 بندًا، **صفر** بنود لها كمية وسعر معا. في v1.0.7: 15 بندًا، **15** بندًا لها كمية وسعر، مع الإشارة إلى **14** بندًا تحتاج مراجعة بسبب اختلافات حسابية أو التباس العدد/الوزن. هذه نتائج المحلل المحلي على النص المرسل، وليست ضمانًا لدقة تصوير الفاتورة الأصلية أو لخدمة OCR نفسها.

## ما تغير

1. قراءة أعمدة جدول Markdown بالأسماء والمواضع الصحيحة، مع استبعاد فواصل الجدول وصفوف المجموع والأسطر الفارغة. الرقم التسلسلي لا يدخل الكمية أو السعر.
2. دعم أرقام 0-9 والأرقام العربية ٠-٩ والفارسية ۰-۹، والفاصلة العشرية مثل `٠,٨`، والتنسيقات المعروفة لفواصل الآلاف. يسمح إدخال الكمية والسعر والخصم بلوحة أرقام عربية ولا يعتمد على `input type=number` الذي يرفض بعض هذه المحارف.
3. عرض الكمية والسعر اللذين قرأتهما الخدمة حتى إذا اختلف الحساب، مع إظهار قيمة الإجمالي المقروءة من الفاتورة مستقلة عن إجمالي الضرب الحسابي. **لا يُعدّل البرنامج رقمًا مستخرجًا تلقائيًا حتى يبدو المجموع متطابقًا.**
4. عند وجود عمودي «العدد» و«كيلو صافي»، تُجرب المطابقة الحسابية أولًا؛ ثم تُراعى وحدة المادة المعروفة، وتُعلّم الحالات غير المحسومة للمراجعة. لا تتحول 8.4 كغ إلى 8.4 غرام تلقائيًا: الوحدة المقروءة يجب أن تكون متاحة للمادة، وإلا يُطلب اختيارها.
5. لكل بند غير متأكد من قراءته تنبيه وخانة «راجعت الأرقام والوحدة مع الفاتورة». **لا يسمح حفظ ونشر الفاتورة قبل تأكيد البنود الموسومة**، مع استمرار نافذة مراجعة الفرق الإجمالي.
6. زر واضح بعنوان **«تحديث البنود من النص المحفوظ»** بجانب «استخراج» يظهر للصور التي سبق استخراج نصها، ويعمل دون إرسال صورة أخرى إلى OCR. إذا كانت هناك بنود حاليًا، يطلب تأكيدًا قبل استبدالها حتى لا تضيع مراجعة يدوية. ويمكن الاحتفاظ بنص OCR مخفيًا كما سبق.
7. زر «مسح التحديدات» بتصميم مناسب للموقع وأيقونة واضحة وإظهار تركيز لوحة المفاتيح؛ يمسح المستطيلات الملوّنة فقط دون حذف الصورة أو البنود أو النص المستخرج.

## طريقة نشر هذه النسخة

1. **لا يوجد SQL جديد للإصدار v1.0.7**. إذا كنت قد نفذت SQL الخاص بالأسماء الثانوية في v1.0.6 فلا تكرره لمجرد نشر 1.0.7. إذا لم تنفّذه أصلًا، اقرأ دليل v1.0.6 وطبّق ترحيله مرة واحدة حسب التعليمات.
2. احتفظ بملف `config.js` الموجود لديك على الاستضافة، وارفع جميع ملفات ZIP الخاص بالإصدار v1.0.7 إلى جذر الموقع **مع الاستبدال الكامل لبقية الملفات**.
3. امسح الذاكرة المؤقتة للمتصفح بتحديث قوي، وتحقق أن التذييل يعرض **Web v1.0.7**.
4. افتح الصورة القديمة في «الصور - إدخال سريع»، ثم اضغط **«تحديث البنود من النص المحفوظ»**. اضغط تأكيد إذا كنت تريد استبدال البنود السابقة، ولن تُرسل الصورة إلى خدمة OCR. إذا لم يكن النص محفوظًا، عندها فقط استخدم زر «استخراج».
5. طابق الكمية والسعر مع صورة الفاتورة، واختر وحدة الشراء الصحيحة، واربط المواد غير المعروفة. ضع علامة تأكيد بجانب البنود التي راجعتها. تحقق من مجموع البنود مقارنة بالمجموع المطبوع قبل الحفظ النهائي. **لا تعِد نشر فاتورة سبق حفظها في المشتريات**.

## الحماية والاختبارات

- لم تتغير دوال حفظ الفواتير أو نشرها (`createPurchase` / `addPurchaseItem` / `postPurchase`) ولم تُمسّ بيانات Supabase أو الصناديق والأوردرات والرواتب والمخزون خارج عملية نشر عادية يجريها المستخدم.
- ما زال النص والصورة محفوظين في IndexedDB داخل المتصفح كما كانا، ولم تتغير خدمة Edge Function أو المحرك 3.
- اختبارات Node المحلية: **316 اختبارًا، 309 ناجحة، صفر فشل، 7 متروكة**. تتضمن اختبارًا حرفيًا لجدول النص الوارد من المستخدم، وتأكيدًا أن تصحيح الفاصلة العشرية وحقول المراجعة لا يسمحان بالنشر التلقائي لأرقام مشكوك فيها.
- **لم يجر اختبار فعلي على Supabase الخاصة بالمستخدم أو على خدمة OCR الحية**؛ فحص المتصفح التفاعلي كان محجوبًا في بيئة الاختبار. الدقة النهائية لأرقام فاتورة يدوية تتطلب مراجعة صورة المصدر؛ حتى وجود مستطيلات تحديد لا يضمن قراءة بلا أخطاء.
