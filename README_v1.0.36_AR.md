# Maria-CFO Web v1.0.36 — إصلاح الإدخال الأول لفواتير شراء الأمين

هذا تحديث **فوق v1.0.35**، لا يعيد تصفير قاعدة البيانات ولا يغيّر ملف Excel الأصلي. لا يتضمن اتصالًا مباشرًا بقاعدة Supabase الخاصة بالمطعم.

## ما كشفه فحص الملفات والكود

- ملف **`حركة تفاصيل الفواتير شراء.xlsx`**: 1,034 فاتورة، 4,614 بندًا، 28 موردًا، 758 اسم مادة مختلفًا، وصافي 20,770,693.05 ل.س. الفاتورة الأولى `شراء: 12` فيها **209 بنود**. هناك **3 وحدات ناقصة** (أسطر 33 و63 و1736)، ولا يجوز تخمين وحدتها؛ يوفر المستورد موافقة صريحة لقبول «قطعة» مؤقتًا.
- **السبب البرمجي المؤكد لضعف الأداء:** المستورد الأصلي يستدعي تحديث مجاميع فاتورة الشراء بعد **كل بند**، بدل مرة واحدة بعد انتهائها؛ أول فاتورة كبيرة تؤدي إلى عشرات آلاف عمليات التجميع المتكررة. كما أضاف v1.0.35 قيد الصندوق ضمن معاملة إنشاء الفاتورة؛ أي فشل نقدي قادر على إلغاء الفاتورة نفسها. واجهة v1.0.35 تخفي رسالة قاعدة البيانات الحقيقية. **لا يمكن تحديد خطأ الخادم الدقيق دون سجل Supabase؛ هذا الإصدار يصلح السببين المحتملين ويعرض السبب إن بقي خطأ آخر.**
- ملف **`2-المنيو-والمواد-بدون-أساسيات.xlsx`**: شيت المواد فيه 493 مادة، وشيت المنيو فيه 199 وجبة و861 سطر مكون. 175 وصفة ما زالت تحتاج مراجعة/استكمال. ورقة `المواد` مطابقة لملف **`المواد.xlsx`** المنفصل؛ **لا ترفعه مرتين**.
- ملف **`حركة تفاصيل الفواتير مبيع.xlsx`**: 6,044 فاتورة، 63,674 بندًا. توجد 321 تسمية مختلفة **دون ورقة مطابقة معتمدة داخل الملف**؛ سيحاول الخادم المطابقة الدقيقة/الأسماء الثانوية، والباقي يظل غير مربوط إلى أن تُعتمد المطابقة. لا تتوقع تصفية جميع تكاليفها تلقائيًا.
- ملف **`الأساسيات.xlsx`**: يحتوي 287 اسمًا من التجهيزات، لكن **كل خانة `العدد الفعلي` فارغة**، ولا يطابق الصيغة التي يقبلها مستورد الأساسيات الحالي (كشف مخزون بأعداد فعلية ومواقع). **لا تُدرجه في استيراد المواد أو الجرد، ولا تضع أصفارًا مختلقة.** يحتاج تحويلًا لكشف تجهيزات بعد جردها أو إدخال أسمائها عبر شاشة الأساسيات. لا يُحسب من جرد المواد الغذائية.
- **`نموذج-الجرد-الرسمي.xlsx`**: 493 صف مادة **بكميات وتواريخ فارغة**. لا يمكن ترحيل كمية جرد قبل تعبئتها ميدانيًا. اجعله آخر ملف.

## تثبيت التحديث بالترتيب

1. خذ نسخة احتياطية من قاعدة Supabase والموقع كاملًا. جرّب التحديث على نسخة تجريبية أولًا.
2. تأكد أن ملفات قواعد البيانات للإصدار السابق v1.0.35 **نُفّذت أصلًا بنجاح**.
3. في **Supabase → SQL Editor** نفذ الملف الجديد مرة واحدة: `database/Maria-CFO-Web-v1.0.36-Purchase-Import-Reliability.sql`. لا تشغّل ملفات RESET. إذا ظهر `V136_REQUIRES_V135_AND_V126_MIGRATIONS` فهذا يعني أن ترحيلًا سابقًا ناقص؛ أتمّه قبل المتابعة.
4. ارفع محتويات `Maria-CFO-Web-Live-v1.0.36-Purchase-Fix.zip` إلى الموقع **دون حذف ملف الاتصال `config.js` الموجود فيه حاليًا**، ثم حدّث المتصفح تحديثًا كاملًا. تأكد من ظهور `v1.0.36`.
5. اختياريًا، تحقّق عبر الملف **`database/Maria-CFO-Web-v1.0.36-VERIFY-READONLY.sql`** في SQL Editor: النتائج `ok=true`، وراجع الحركات النقدية المؤجلة.
6. داخل **الإعدادات ← الإدخال الأول**، استخدم **ترتيب الملفات أدناه**. عند وجود واردات سابقة صحيحة، يُعيد البرنامج استقبال الملف نفسه بصورة لا تكرر الفاتورة. لا ترفع نسخة أخرى معدلة عشوائيًا لتجاوز تعارض البصمة.

## تفاصيل التصحيح

- **فواتير الشراء الكبيرة:** تجميع الدفعات حسب عدد الفواتير **وعدد البنود** بدل 12 فاتورة عمياء. الفاتورة `شراء: 12` ذات 209 بنود تُرسل وحدها للحفاظ على ذرية بياناتها.
- **قاعدة البيانات:** كل بند يُضاف مع فحص الوحدة والتحويل والسعر نفسه الموجود في الدالة الأصلية، لكن تجميع إجمالي فاتورة الشراء يتم **مرة واحدة عند انتهاء بنود الفاتورة** بدلًا من كل بند.
- **حركة الصناديق:** خطأ صرف/قبض الصندوق **لا يُلغي أرشفة الفاتورة**؛ تحفظ المعاملة النقدية التي تعذرت في جدول `v136_historical_cash_deferred` مع رمز خطأ وسببه، وتظهر في شاشة «ترحيل الفواتير القديمة». استردادها يتم بعد مطابقة أرصدة الصناديق والتأكد من عدم تسجيلها يدويًا؛ يمنع تكرار القيد بمفتاح المصدر.
- **رسائل الفشل:** تعرض رقم الفاتورة، رقم سطر المصدر، اسم المادة، SQLSTATE ورسالة الخطأ في الشاشة، بدل رسالة عامة غير مفيدة.
- **الإدخال الأول:** أصبحت واجهة الخطوات ترتب المبيعات التاريخية **قبل الجرد**، ويظل الجرد الفعلي آخر مرحلة.

## مهم بشأن الصناديق

وجود رصيد **0** في الصندوق العام لا يثبت أن نقد المطعم التاريخي كان صفرًا. بعض قيود الشراء القديمة قد تفشل إذا لم يتوفر رصيد/جلسة صندوق أو كانت الفاتورة مُسواة. عندها **تنجح أرشفة الفاتورة لكن تظهر حركة الصندوق معلّقة**؛ لا تعتبر المبلغ مصروفًا حتى تعتمد المطابقة. لا تضع أرصدة افتتاحية مختلقة ولا تضغط «ترحيل» قبل مطابقة كشوف الصناديق.

## حدود الاختبار

- اجتاز ملف الشراء نفسه فحص المحلل المحلي: **1,034 فاتورة / 4,614 بندًا / 3 وحدات ناقصة**، مع 174 دفعة استيراد دون ضياع أي فاتورة. اجتاز ملف المنيو والمبيعات فحوص قراءة الأسماء والصفوف محليًا.
- فُحصت صياغة JavaScript وعناصر الترحيل SQL بالمراجعة الثابتة، **لكن لم أُجرِّب تنفيذ SQL أو إدخال المعاملات على قاعدة Supabase المتصلة عندك**. لذلك اختبر على Staging ثم راقب أول دفعة في الموقع. عند استمرار الفشل ستعرض v1.0.36 رسالة الخطأ الدقيقة؛ انسخها قبل أي محاولة لتصفير أو تعديل الملف.
