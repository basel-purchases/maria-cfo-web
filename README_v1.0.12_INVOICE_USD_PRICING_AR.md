# Maria CFO Web v1.0.12 — بطاقات الفواتير وإصلاح اعتماد التسعير

## التثبيت بالترتيب

1. خذ نسخة احتياطية من قاعدة البيانات، واحتفظ بنسخة الموقع الحالية.
2. في Supabase SQL Editor شغّل `database/Maria-CFO-Web-v1.0.12-PRICING-REPAIR.sql` **كاملًا**. انتظر نتيجة `SELECT` الأخيرة؛ يجب أن تكون قيمة `initialization_rpc_ready` و `exchange_rpc_ready` هي `true`. الملف يضم متطلبات v1.0.10 وv1.0.11، ولا يلزم تشغيلهما مجددًا.
3. ارفع جميع ملفات الموقع من ZIP الجديد إلى الاستضافة مع **الإبقاء على `config.js` الحالي**. لا ترسل مفاتيح الاتصال لأحد.
4. حدّث المتصفح بقوة وافتح صفحة المواد وتأكد من ظهور Web v1.0.12، ثم جرّب تسعيرًا مرجعيًا على قاعدة تطوير أو نسخة احتياطية متى أمكن.
5. إن ظهر فشل عند التسعير، انسخ **النص ورمز الخطأ الظاهرين داخل نافذة التسعير**. لا تكرر اعتماد عملية غير مؤكدة قبل تحديث المواد والتحقق من نتائجها.

## سبب صعوبة اعتماد التسعير

واجهة v1.0.11 كانت تطلب تأكيدًا ثانيًا داخل نافذة التعديل، ولم تبقِ رسالة خطأ Supabase أمام المستخدم. كما استخدم SQL السابق `FOR UPDATE` داخل استعلام تجميعي ومعه تعديل البيانات والتدقيق، وهي صياغة معقدة يصعب تشخيصها عند الفشل. أزلنا التأكيد المتداخل، ووضعنا رسالة ثابتة، وأعدنا كتابة مسار المعالجة بحيث تُؤخذ أقفال المواد قبل التنفيذ وتُحفظ الأسعار وتاريخها داخل معاملة PostgreSQL واحدة، وتُسجَّل أسعار الصرف فقط بعد نجاح التعديل.

**حد التحقق:** لا يوجد اتصال بقاعدة Supabase الحية، لذلك لا يمكن الجزم أن هذه كانت رسالة الخطأ التي ظهرت هناك؛ لا يمكن إثبات السبب النهائي إلا برمز خطأ Supabase الفعلي. لم نشغّل SQL على قاعدة المستخدم، ولا يمكننا إعلان نجاح الاعتماد قبل اختباره على الاستضافة.

## قواعد التسعير

- سعر الليرة المجهول أو الصفري لا يتحول إلى سعر دولار؛ ولا تُنشأ له قيمة عند تغيير الصرف.
- لا تغيّر العملية آخر فاتورة شراء أو سعر آخر شراء أو حركات المخزون. السعر بالدولار وسعر الليرة المرجعي حقول منفصلة.
- عند تحديث سعر الدولار من الإعدادات تظهر نافذة «تحديث الأسعار» أو «عدم التحديث» أو «إلغاء»؛ لا يعاد تسعير المواد غير المعروفة.
- إذا فشل أي تحديث أو حفظ سجل التغيير، تُلغى المعاملة كاملة، دون نجاح جزئي.

## مراجعة بنود الفواتير بالصور

- يظل موضع الصورة في اليمين، والبنود في اليسار مع تمرير عمودي مستقل.
- في كل بند: الاسم والمادة؛ ثم **الكمية يمينًا، والوحدة وسطًا، وسعر الوحدة يسارًا**؛ ثم الخصم والإجمالي وزر الحذف أقصى اليسار.
- شريط أرقام أعلى البنود؛ النقر على رقم ينتقل إلى البند داخل القائمة دون تحريك صفحة الصورة.
- تعديل الكمية والسعر والخصم يحسب الإجمالي ويفحص صلاحية زر حفظ الفاتورة دون إعادة رسم القائمة أو إرجاع التمرير للأعلى.
- أُزيل نص «الجدول بلا عناوين موثوقة...» من النتائج الجديدة ونصوص المسودات القديمة الظاهرة.
- ما زالت مراجعة اسم المادة والكمية والوحدة ضرورية عند غموض OCR؛ لا تُنشَر حركات مالية تلقائيًا.

## دفتر اليومية

الملف `دفتر اليومية1.xlsx` يحتوي قيود مبيعات مرتبطة بكاش1/كاش2/مبيع مطعم، وأرقام طاولات وقيم إجمالية وحسابات ضرائب، لكنه ليس ملف بنود أوردرات منظّمًا بوجبات وكميات وأسعارها. يحتوي كذلك سندات شراء بأرقام فواتير وأسماء موردين ومبالغ إجمالية، لا كل مواد الفاتورة وكمياتها بصورة موحدة. يمكن استيراده **للمطابقة المالية فقط** بعد تصميم حذر ضد التكرار؛ أما بند الأوردر أو بند الفاتورة فلا يؤخذ من هذا الملف بوصفه سجلًا تفصيليًا كاملًا. لم تُستورد أي حركة من هذا الملف إلى Supabase في هذا التحديث.

## الاختبار

`node --test tests/*.test.mjs` يفحص منطق JavaScript والوصلات والتوافق النصي للـSQL. اختبارات المتصفح الحي وSupabase الفعلية لا تتوفر في هذه الجلسة.
